# Ricky 会客厅 Agent 与 RAG 架构说明 V1

## 一句话说明

这套架构不是“先把所有知识塞给模型，再期待模型自己守规矩”，而是由服务端先判断身份、额度和知识权限，只取少量最相关内容，再让当前模型按统一的 Ricky 行为协议生成回答。

因此，替换模型只是在更换“理解与生成引擎”，不会同时更换身份、权限、知识范围和运营规则。

## 一次提问如何执行

```mermaid
flowchart LR
    A["访客提问"] --> B["输入与使用量检查"]
    B --> C["识别访客权限"]
    C --> D["筛出可访问知识库"]
    D --> E["有限检索相关片段"]
    E --> F["编译 Ricky 行为协议"]
    F --> G["调用当前主模型"]
    G --> H["隐藏路径与敏感信息"]
    H --> I["回答或引导申请权限/留资"]
    I --> J["记录最小运行数据"]
```

执行顺序本身就是约束。模型无法绕过前面的额度和权限检查，因为没有权限的知识根本不会进入模型上下文。

## 五层职责

| 层次 | 负责什么 | 是否随模型切换 |
|---|---|---|
| 服务端强约束 | 用量限制、权限过滤、允许使用的工具、密钥保护 | 不变 |
| Agent 行为协议 | 身份、回答范围、表达风格、承诺边界、禁止事项 | 不变 |
| 知识检索 | 从已关联且有权访问的知识库中有限召回 | 不变 |
| 会话上下文 | 当前问题与受限长度的历史对话 | 不变 |
| 模型连接 | 理解上述信息并生成自然语言 | 可替换 |

后台保存的是结构化行为字段，而不是一段难以维护的超长提示词。服务端每次调用前将这些字段、公开资料和本轮召回内容编译为统一协议，再转换成 OpenAI 兼容请求。

## 为什么不加载全部知识

全部加载会带来四个问题：

1. 上下文成本持续增长；
2. 无关内容稀释真正相关的信息；
3. 权限边界更难控制；
4. 知识更新后难以判断本轮实际用了什么。

V1 的处理方式是：

- Markdown 按标题层级和字符预算分块；
- 先按 Agent 关联范围、RAG 开关和访客权限过滤；
- 再按问题与标题/正文的相关度排序；
- 默认最多召回 6 个片段、总计不超过约 5,500 个字符；
- 前台只展示回答，不罗列知识库、文件名和真实来源路径；
- 管理员测试台可查看命中的语义知识库，便于调试。

这已经能避免“每次把所有知识送给模型”的浪费。未来资料量显著增加时，可以只替换检索实现为混合检索或向量检索，不需要重做 Agent 和前台。

## 知识权限如何生效

每个知识库有四个独立控制：

- `默认权限`：公开、授权账号、仅本人；
- `参与 RAG`：是否允许进入任何检索；
- `会客厅展示`：是否在前台显示知识能力与权限信号；
- `Agent 关联`：当前数字接待 Agent 是否允许使用。

最终可检索范围取四者交集，而不是任意一项单独决定。

V1 公开页面统一按匿名访客处理；管理员测试台按本人权限处理。注册、受邀登录和按账号授权已在角色模型中预留，待确定邮箱验证码方案后再接入。

## 模型切换后为什么仍会按预期行为

模型并不是直接读取后台表单。实际调用时，服务端会完成：

1. 读取已发布的 Agent 版本；
2. 执行不可关闭的额度与权限规则；
3. 获取本轮可用公开资料和知识片段；
4. 将身份、范围、风格、知识规则、权限边界、承诺边界、回答结构、转化规则和禁止事项编译成系统协议；
5. 使用统一消息格式调用当前主模型；
6. 对返回内容再次做路径、密钥和长度清理。

不同模型对文字指令的理解能力仍可能存在差异，所以后台保留标准问题测试台。切换主模型前，应至少验证：

- 回答是否像 Ricky，而不是泛化客服；
- 是否能直接回答职业、金融产品和 AI 应用问题；
- 证据不足时是否承认边界；
- 是否会泄露路径、内部标识或提示词；
- 私密问题是否引导申请权限；
- 合作类问题是否只引导沟通，不擅自承诺和报价。

## 工具权限

工具分为三类：

- 必需：权限检查、使用量检查等，服务端强制执行，后台不能关闭；
- 可配置：权限申请、留资等业务动作，可按运营需要打开或关闭；
- 禁止：修改知识、批准权限、发送外部消息、开放式联网等，不会提供给公开 Agent。

V1 的“工具”主要是受控业务动作，不让模型自由操作外部系统。这比给模型大量工具再靠提示词限制更稳妥。

## 运行记录与隐私

后台记录页面浏览、匿名访客标识、问题短预览、回答模式、模型、召回数量、Token、耗时和下一步动作。访客联系方式使用 AES-256-GCM 加密后落盘。

不会进入运行记录的内容包括：

- API Key；
- 完整系统提示词；
- 完整模型回答；
- 原始知识片段；
- 真实文件路径；
- IP 地址。

## 后续升级顺序

1. 先接入真实主模型并用标准问题完成质量基线；
2. 再接入受邀登录与知识库授权；
3. 访问量或资料量明显上升后，再迁移数据库与混合检索；
4. 最后才考虑更复杂的多 Agent 或外部工具。

当前阶段保持单一数字接待 Agent，能更容易校准 Ricky 的内容质量、边界和表达一致性。
