# Ricky Twin 管理端在线升级设计

## 1. 目标

为 Ricky Twin 增加统一的“系统更新”管理页面，使管理员可以查看当前版本、检测私有 GitHub 仓库中的最新正式版本，并执行一键更新和应用重启。升级必须以保护既有前台内容、知识库、Agent/模型配置、密钥和运行记录为最高约束，任何异常都不得静默初始化或覆盖存量数据。

## 2. 核心边界

- 应用代码封装为不可变 Docker 镜像；运行数据、环境密钥和备份位于镜像之外。
- Web 应用不挂载 Docker Socket，也不直接执行 Docker 命令。
- 管理端只负责版本发现、兼容性判断、写入更新/回滚请求和展示状态。
- 宿主机独立更新器监听请求文件，完成备份、拉取镜像、数据预检、切换、重启、健康检查和自动回滚。
- 更新只接受预设 GitHub 仓库发布的不可变镜像摘要，拒绝任意镜像地址或任意命令。
- 开发环境可以显示版本和模拟状态，但未启用更新器时不得伪装成可在线升级。

## 3. 管理端信息架构

“系统能力”增加独立入口“系统更新”，页面集中展示：

1. 当前版本、构建提交、当前数据结构版本和部署模式；
2. 最新正式版本、发布时间、更新说明和数据兼容结论；
3. 上次检测时间、更新器是否在线、最近一次备份；
4. “检查更新”“一键更新并重启”“回滚上一版本”三个操作；
5. 更新阶段进度：等待、备份、拉取、校验、迁移、重启、健康检查、成功、回滚、失败；
6. 重启期间自动重连，恢复后继续读取同一个持久化状态文件并展示最终结果。

更新按钮只在以下条件全部成立时开放：存在更高版本、数据结构兼容、更新器已启用、当前没有其他更新任务。回滚按钮只在存在可验证的最近备份时开放。

## 4. 版本发现与发布物

版本源使用私有 GitHub Releases。服务端通过只读 Token 查询最新 Release，并读取 `update-manifest.json` 资产。清单包含：

```json
{
  "schemaVersion": 1,
  "version": "0.2.0",
  "releaseTag": "v0.2.0",
  "image": "ghcr.io/ricky940828/ricky.twin@sha256:...",
  "publishedAt": "2026-08-12T00:00:00Z",
  "minimumDataSchemaVersion": 1,
  "maximumDataSchemaVersion": 1,
  "requiredUpdaterVersion": "1.0.0",
  "notes": ["新增管理端在线升级"]
}
```

GitHub Actions 在推送 `v*` 标签后执行测试和构建，将镜像推送到私有 GHCR，以构建得到的 digest 生成清单，再创建 GitHub Release。管理端只使用正式 Release，不把 `main` 分支上的未发布代码当作新版。

## 5. 持久数据与兼容策略

生产部署固定使用：

```text
/opt/ricky-twin/
├── compose.yaml
├── config/.env
├── deploy/image.env
├── data/
│   ├── meta.json
│   ├── content/
│   ├── knowledge/
│   ├── agent/
│   ├── runtime/
│   └── system-update/
└── backups/
```

`data/meta.json` 记录 `dataSchemaVersion`。现有未带元数据的数据目录按版本 1 接管，不改写业务文件。新版本只允许：

- 为缺失的新字段补默认值；
- 通过明确、可测试、逐版本的迁移函数改变结构；
- 在完整备份之后执行迁移；
- 迁移失败立即恢复整个数据快照。

生产模式读取到损坏或不兼容的工作区文件时直接报错并使健康检查失败，不再恢复为空工作区。原始文件保持不动，自动回滚到旧镜像和升级前数据。

`RICKY_SECRETS_KEY`、后台密码、GitHub/GHCR Token 和会话密钥位于 `/opt/ricky-twin/config/.env`，不进入镜像和备份日志。`RICKY_SECRETS_KEY` 必须跨版本稳定，否则已有模型 Key 和留资密文无法解密。

## 6. 更新事务

一次更新按以下状态机执行：

```text
requested
  → pulling
  → backing_up
  → validating
  → migrating
  → restarting
  → health_check
  → succeeded
```

任一步失败均进入：

```text
rolling_back → rolled_back
```

若回滚自身失败则进入 `failed`，状态文件保留明确原因和备份路径，但不包含密钥。更新器使用文件锁保证同一时间只有一个任务。备份采用不可变时间戳目录，并包含数据快照、原镜像引用和部署元数据。

健康检查必须同时确认：

- HTTP 服务恢复；
- 实际运行版本等于目标版本；
- 数据结构版本可读；
- content、knowledge、agent、runtime 四个工作区均可解析；
- 管理端更新状态 API 可访问。

## 7. 安全与权限

- 所有更新 API 沿用管理员会话保护；浏览器不能提交镜像地址。
- 服务端只根据最近一次可信 Release 清单生成请求。
- 宿主更新器再次校验版本格式、镜像前缀、digest、目标数据版本和请求时效。
- GitHub Token 仅需私有仓库读取权限；GHCR Token 仅需私有包读取权限。
- 更新器不开放公网端口，通过共享数据目录和 systemd path unit 接收请求。
- 更新日志不打印 Token、环境文件内容或模型 API Key。

## 8. 故障处理

- GitHub 无法访问：保留当前版本，页面展示检测失败和最近一次成功检测结果。
- 没有更新器：允许查看版本，禁用一键更新并显示部署提示。
- Release 清单不完整或镜像不在允许前缀：拒绝更新。
- 数据不兼容：更新按钮禁用，提示必须先安装中间版本。
- 重启期间浏览器请求失败：页面持续退避重试，不把网络中断判定为更新失败。
- 新容器未通过健康检查：恢复旧镜像和完整数据快照，重启旧版本。

## 9. 验收标准

1. 管理端能看到当前版本和系统更新入口。
2. 能识别“已是最新”“发现新版”“检测失败”“数据不兼容”“更新器未启用”。
3. 一键更新只生成经过服务端验证的请求，不能由浏览器指定镜像或命令。
4. 模拟升级成功后，状态为成功且当前版本改变。
5. 模拟健康检查失败后，旧镜像与所有数据被恢复。
6. 升级前后的知识库 Markdown、前台草稿/正式版本、Agent/模型设置和运行记录校验和一致；仅显式迁移字段允许变化。
7. 损坏工作区在生产模式下不得被初始数据覆盖。
8. 全量单元测试、类型检查、Lint、生产构建和关键管理端端到端测试通过。
